# agent-cli-bash

[English](README.en.md) | [中文](README.md)

Turn a sentence of natural language into a bash command, right in your terminal. Type `a` + a space + what you want, DeepSeek returns the command, and after your confirmation it runs in your **current shell**.

```console
$ a find the 5 largest files in the current directory
du -ah . 2>/dev/null | sort -rh | head -5
Execute? [y=yes n=no i=ignore] y
...
```

Pure bash/zsh — the only dependencies are `curl` and `jq` (or `python3`). No other runtime.

## Install

```bash
git clone <this repo>
cd agent-cli-bash
./install.sh          # writes to ~/.zshrc or ~/.bashrc based on $SHELL
source ~/.zshrc       # or restart your terminal
```

Uninstall: `./install.sh --uninstall`

After installing, keep `a.sh` (the entry) and `lib/` (the harness) together in the same directory; your rc only gets one `source .../a.sh` line, and a.sh loads `lib/` itself.

## Windows (PowerShell port)

The `win/` directory is an equivalent PowerShell port (works on both Windows PowerShell 5.1 and PowerShell 7+), mirroring the bash version file by file: `win/a.ps1` (entry + product layer), `win/lib/` (the a-api/a-ctx/a-exec harness domains), `win/install.ps1`. Zero external dependencies — HTTP goes through the system-provided `curl.exe` (Windows 10 1803+), JSON through the built-in `ConvertFrom-Json` (no jq needed).

```powershell
git clone <this repo>
cd agent-cli-bash\win
powershell -ExecutionPolicy Bypass -File install.ps1    # pwsh 7 works too
# reopen PowerShell, then: a find the 5 largest files in the current directory
```

- Installing adds one dot-source `win\a.ps1` line to `$PROFILE`; uninstall with `install.ps1 -Uninstall`
- Usage (`a` / `a -p` / `a -y` / `a ask` / `a -c` / `a --show` / `a setup`), multi-turn context, ASK clarification, and risk-tiered confirmation all match the bash version; the risk rules cover PowerShell/cmd commands (`Remove-Item -Recurse -Force`, `Format-Volume`, `iwr | iex`, …)
- Shares the same config path and format as the bash version (`~\.config\agent-cli-bash\config`)
- Differences: PowerShell functions have no exit code of their own — the result code lands in `$A_LAST_RC`; pipelines spawn no subshell, so `cd` and `$env:` assignments take effect in the current session (plain `$x=` does not persist — ask the AI to use `$env:` or `$global:` when persistence matters)
- Local tests: `pwsh -NoProfile -File win\test.ps1` (needs python3 for the mock server); `win/` also runs under pwsh on macOS/Linux, which is where the tests are verified

## Configuration

Multiple model providers are supported — run `a providers` to list the built-ins:

| Provider | `A_PROVIDER` | Default model | Key env var |
| --- | --- | --- | --- |
| DeepSeek (default) | `deepseek` | `deepseek-chat` | `DEEPSEEK_API_KEY` |
| ChatGPT / OpenAI | `openai` | `gpt-4o-mini` | `OPENAI_API_KEY` |
| Kimi / Moonshot | `kimi` | `kimi-k2-0905-preview` | `MOONSHOT_API_KEY` |
| Tongyi Qwen | `qwen` | `qwen-plus` | `DASHSCOPE_API_KEY` |
| Zhipu GLM | `zhipu` | `glm-4-flash` | `ZHIPU_API_KEY` |
| xAI Grok | `grok` | `grok-3-mini` | `XAI_API_KEY` |
| Ollama (local) | `ollama` | `qwen3:8b` | none needed |
| OpenRouter | `openrouter` | `openai/gpt-4o-mini` | `OPENROUTER_API_KEY` |

Switching to ChatGPT is just:

```bash
export A_PROVIDER=openai
export OPENAI_API_KEY=sk-xxx     # already set? then nothing to do
```

Or run `a setup` for an interactive wizard — pick a provider, paste the key (hidden input); it merges into `~/.config/agent-cli-bash/config` with 600 permissions and takes effect immediately. You can also edit that file directly (a template is generated by `install.sh`):

```ini
A_PROVIDER=kimi
A_API_KEY=sk-xxx                 # unified key; if unset, the provider's env var above is read
# A_MODEL=kimi-k2-0905-preview   # optional, overrides the default model
# A_BASE_URL=...                 # optional, overrides the endpoint; use this for any other OpenAI-compatible gateway
# A_MAX_RETRIES=3                # optional, auto retries on network errors / 429/5xx (0 disables)
# A_MAX_CONTEXT_CHARS=24000      # optional, session context character budget
# A_TIMEOUT=60                   # optional, per-request timeout in seconds
# A_DIR_ENTRIES=15               # optional, directory-entry context cap (0 disables); relevant entries first, rest by mtime
```

Precedence: environment variables > config file; `A_API_KEY` > provider-specific vars (e.g. `OPENAI_API_KEY`). With only the legacy `DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL` / `DEEPSEEK_MODEL` set, behavior is unchanged from previous versions. `A_MAX_RETRIES` controls automatic retries on network errors and HTTP 429/5xx (default 3, exponential backoff honoring `Retry-After`; 0 disables; client errors like 401 are never retried). `A_TIMEOUT` sets the per-request timeout (default 60 s). `A_DIR_ENTRIES` caps the directory entries injected as context (default 15, 0 disables).

Key safety: the config file is automatically tightened to 600 permissions (owner-only) both when loaded and when written by `a setup`; request headers are passed to curl via a `-K` temp file, so the key never appears in process arguments (invisible to `ps`).

## Usage

| Command | What it does |
| --- | --- |
| `a <natural language>` | Generate a command, confirm, execute |
| `a -p <natural language>` | Print the command only, never execute (pipe-friendly) |
| `a -y <natural language>` | Skip the normal confirmation (dangerous commands still ask) |
| `a ask <question>` | Free-form Q&A: get an answer directly, no command generated or executed; pipes supported |
| `a -c` | Clear this session's conversation context |
| `a --show` | Inspect session context (turns / size / trimming) |
| `a providers` | List built-in model providers |
| `a setup` | Interactive provider & key setup (writes the config with 600 permissions) |
| `a -h` / `a --version` | Help / version |

Confirmation prompt `Execute? [y=yes n=no i=ignore]`: `y` runs it; `n` or Enter declines with exit code 130 (an explicit refusal you can catch with `||` in scripts); `i` skips it with exit code 0. Executed commands are written to shell history — press ↑ to get them back.

**Multi-step commands are confirmed line by line**: when the AI returns multiple lines (a sequence of steps), nothing runs in one shot — each step is shown and decided individually:

```console
$ a back up the config and clean up temp files
Step 1/3: cp app.conf app.conf.bak
⚡  Write operation — modifies files or state
Run this step? [y=yes n=stop remaining i=skip] y
Step 2/3: sudo rm -rf /tmp/cache
⚠  Dangerous operation (privilege escalation / forced deletion / system-level writes) — verify every character
Run this step? [y=yes n=stop remaining i=skip] n
Stopped — remaining steps will not run
```

- `y` runs this step and continues; `n` stops all remaining steps (exit code 130 if nothing ran); `i` skips this step and moves on.
- Every step gets a static risk check with color highlighting: dangerous commands such as `sudo`/`su`, `rm -rf`, `dd`, `git push --force`, `git checkout --`, `curl \| sh` are shown **entirely in red**; write operations such as `rm`, `mv`, overwriting redirects `>`, `git push`, package installs are shown **in yellow** (pattern-based — it assists, but does not replace, your own review).
- **Dangerous commands always require an explicit human decision: even `a -y` will not auto-run them**, and in non-interactive environments (scripts/CI) they are refused outright.
- Generation is **streamed live** (dimmed gray); the final command is then shown again with risk highlighting before you decide.

**Streaming**: requests use SSE, so the command appears as the model types it — no waiting for the full response.

## Multi-turn conversation & context

Within the same shell session, `a` carries context automatically, so you can follow up like a chat:

```console
$ a list the images in the current directory
find . -maxdepth 1 -name '*.png' -o -name '*.jpg'
Execute? [y=yes n=no i=ignore] y
$ a only the pngs, sorted by mtime, newest first
ls -t *.png
Execute? [y=yes n=no i=ignore] y
$ a the first command errored, fix it
...
```

The context sent to the AI each turn includes:

- piped input (the entire stdin when you do `cat error.log | a explain this error`, capped at 8KB);
- **current environment**: working directory, git branch + uncommitted-change count, and directory entries (cap `A_DIR_ENTRIES`, default 15) — when the directory is large, entries are not blindly truncated in alphabetical order: **entries relevant to your request come first** ("sha256 of linuxiso" surfaces `linuxmint-*.iso` at the top), the rest fill by mtime newest-first, and the header shows the total count;
- previous requests and AI-generated commands from this session (even the ones you declined);
- **exit code and output tail** (last 40 lines) of executed commands — that's why "fix that error" works;
- the last 6 shell history entries you typed by hand (excluding `a` itself), so the AI knows what you've been doing.

**The AI never invents file names — it asks**: the system prompt requires exact names from the context to interpret your loose wording. If the file you refer to is still ambiguous or absent, the AI asks back with a `❓` question (e.g. "multiple iso files here — which one's sha256 do you want?"); type your clarification and the command is **regenerated in the same turn** (at most 3 follow-ups), or press Enter to cancel. Without a terminal (scripts/CI) it prints the question and exits safely without executing anything.

Context is isolated per shell session (separate terminal windows don't interfere); `a -c` clears it anytime. Command (`a`) and Q&A (`a ask`) contexts are stored per mode and never mixed; `a -c` clears both. Size is doubly bounded: at most 40 messages, and within a character budget (`A_MAX_CONTEXT_CHARS`, default 24000 ≈ 12K tokens) **whole turns** are kept from newest to oldest (request + command + result stay together, never split); turns beyond the budget are dropped, the latest turn is always kept.

Use `a --show` anytime to see what has accumulated and what the next turn will actually send:

```console
$ a --show
[run] Session context: 4 messages / 243 bytes, budget 24000, next turn will send 4 / 243 bytes (a -c to clear)
  Turn 1  find the largest files
          Command: du -ah . | sort -rh | head -5
  Turn 2  only the top 3
          Command: du -ah . | sort -rh | head -5
```

When a task needs several sequential steps the AI can return multiple lines, executed one by one after per-step confirmation (see "Multi-step commands" above).

Notes:

- Commands that mutate shell state — `cd`, `export`, `alias`, `source`, etc. — are **executed directly in the current shell** (directory changes, variables and aliases really take effect); their output is not fed back to the AI, and the summary notes this;
- command output and shell history are sent to DeepSeek — in sensitive environments prefer `a -p` and review manually, or avoid using this in sessions that contain secrets;
- other commands' output is captured through a pipe, so full-screen programs like `vim` or `top` display incorrectly when run through `a` — run those directly.

Examples:

```bash
a compress all .png images to 50% quality
a who committed the most in this git repo in the last two weeks
a -p find the most frequent word in a text
cat error.log | a explain this error            # piped content is sent as context (8KB cap)
git diff | a write a commit message for this
dmesg | tail -50 | a                           # with piped input, the description is optional
```

## Security notes

- AI-generated commands are **shown and confirmed by a human before execution**; multi-step commands are confirmed step by step, and **dangerous/privileged commands require explicit confirmation even with `-y`** — in non-interactive environments they are always refused.
- Commands run via `eval` in your current shell, so `cd`, environment variables and aliases all take effect — that's the feature and the risk; read deletion commands carefully before confirming.
- Piped input, command output and shell history are sent to DeepSeek — in sensitive environments prefer `a -p` and review manually, or avoid using this in sessions that contain secrets.

## How it works

The code is split into a product layer and a harness, with dependencies pointing one way:

- `a.sh` — entry & product layer: routing of the `a` command, each capability's system prompt and output parsing (command mode strips fences, handles ASK follow-ups), plus the confirmation/execution UX;
- `lib/a-api.sh` — transport: provider table, config I/O (`a setup`), the SSE streaming client with automatic retries;
- `lib/a-ctx.sh` — context: per-mode conversation storage and trimming, smart directory-entry selection, git/shell-history gathering;
- `lib/a-exec.sh` — execution: command risk classification, shell-state detection, the multi-step confirmation executor and terminal interaction helpers.

At runtime your description plus system/cwd context is sent to the model (`temperature=0`, instructed to return only the command), and executed via `eval` after your confirmation. Adding a capability = one mode function in the product layer (its own prompt and output policy) reusing the harness transport and context — `a ask` is the first example.
